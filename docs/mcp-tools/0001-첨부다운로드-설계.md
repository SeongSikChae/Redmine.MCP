# 첨부파일 다운로드 MCP 도구 — 설계

근거: [0001-첨부다운로드-방안.md](0001-첨부다운로드-방안.md) (`status: done`)

## 합의된 결정

### D1. 바이너리 다운로드 위치 — **A**

- [`RedmineClient`](../../src/Redmine.MCP.Server/Redmine/RedmineClient.cs)에 `GetBytesAsync`를 추가한다.
- 요청별로 `Accept: */*`(또는 동등)를 두고, 전역 `Accept: application/json`은 유지한다.
- `content_url` / `contentUrl`의 **origin 검사**도 이 다운로드 경로에 둔다(Tools에 흩뿌리지 않음).
- 별도 `AttachmentDownloadClient`·Tools에서 `HttpClient` 직접 호출은 하지 않는다.

### D2. MCP 도구 클래스 배치 — **A**

- `AttachmentTools`를 신설하고 `download_attachment`만 둔다.
- [`Program.cs`](../../src/Redmine.MCP.Server/Program.cs)에 `.WithTools<AttachmentTools>()`를 등록한다.
- [`IssueTools`](../../src/Redmine.MCP.Server/Tools/IssueTools.cs)에는 다운로드 도구를 추가하지 않는다.

### D3. 헬퍼/JSON 조립 — **A**

- `AttachmentDownload`(internal static) 파일을 분리한다. 텍스트/base64 판별, 5 MiB 인라인 여부, 응답 JSON 조립만 담당한다(HTTP·디스크 I/O 없음).
- `AttachmentTools`는 식별·메타/본문 호출·`outputPath` 저장·헬퍼 호출만 한다.
- 인코딩 정책을 `RedmineClient`에 넣지 않는다.

### D4. 처리 흐름·오류 — **A** (메타 항상 조회)

1. `attachmentId` 우선, 없으면 `issueId`+`filename`으로 일감 `include=attachments`에서 id 해석(`Ordinal` 파일명 매칭; 0건·중복이면 오류).
2. **항상** `GET attachments/{id}.json`으로 메타를 받는다(`contentUrl`이 있어도 생략하지 않음).
3. 본문 URL: `contentUrl`이 있으면 그것으로(origin 검사), 없으면 메타 `content_url`(origin 검사).
4. `GetBytesAsync`로 바이트 수신. **크기 판정은 실제 바이트 길이**.
5. 5 MiB 초과·`outputPath` 없음 → 오류. 초과·경로 있음 → 저장만(인라인 본문 생략). 이하 → 헬퍼 인코딩 + 선택 저장.
6. 예외: 검증 `ArgumentException`, 업무 `InvalidOperationException`, Redmine `RedmineApiException`, 디스크는 그대로. API 키는 메시지에 넣지 않음.

### D5. README·테스트 — **A**

- `README.md`와 `src/Redmine.MCP.Server/README.md`에 `download_attachment` 절 추가(입력 요약, 5 MiB, `outputPath`는 MCP 서버 호스트).
- 단위 테스트: `RedmineClient.GetBytesAsync`, `AttachmentDownload`, `AttachmentTools`.
- `Redmine22ContractTests`(또는 동등)에 도구 Description 핵심 문구 검증(5 MiB, `outputPath` 서버 호스트 등).
